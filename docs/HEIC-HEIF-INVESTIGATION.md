## Existing behavior that a decoder must preserve

`main_windows.go` funnels command-line arguments, the file picker, and Shell drops through `application.addFile` and `loadImage` in `render_windows.go`. Import is synchronous on the native UI thread. A slow decoder therefore delays the editor and message handling; a goroutine alone would not supply a safe timeout or stop an uncooperative native decoder.

`loadImage` opens a Unicode-capable path with `os.Open`, sniffs the content using `image.DecodeConfig`, and rejects nonpositive dimensions or a product above **40,000,000 pixels** before full decode. It then seeks and calls `image.Decode`, with the existing first-frame fallback for animated WebP. It converts the decoded image into premultiplied 8-bit RGBA, swaps red and blue to BGRA, and retains that buffer for the GDI+ bitmap lifetime. Existing tests cover misleading extensions, Unicode paths, alpha, malformed inputs, AVIF size rejection, and WebP first-frame behavior.

The importer trusts the configuration dimensions when allocating and drawing. A decoder that applies a 90-degree orientation transform only during full decode could return swapped dimensions and be cropped into the old rectangle. A candidate needs configuration/output agreement, including clean aperture and orientation, and checks on coded dimensions as well as displayed dimensions. A small declared display size does not by itself bound coded buffers, grid tiles, auxiliary alpha, reference frames, or metadata allocations.

At 40 million pixels, one 4-byte output buffer is 160,000,000 bytes (about 152.6 MiB); two such buffers alone are about 305.2 MiB, before codec working state, compressed input, and rendering surfaces. These are arithmetic lower bounds, **not measured peak memory**. Typical 48MP images exceed the existing limit and must be rejected; support must not quietly downsample or raise the limit.

There is no existing general ICC/HDR display pipeline in `loadImage`. The passive raised-desktop rendering path also flattens partial alpha and keys out #010203, as already documented in `CONTRIBUTING.md`. A successful decoder test would not establish final compositor color/alpha fidelity. This investigation does not change either behavior.

### Specific source findings

1. **WASM first-image cost:** `heic.go` detects a sequence, calls `DecodeAll`, and returns `h.Image[0]`. `lib/lib.rs`'s `decode_sequence` decodes all frames, converts them all to RGBA, then concatenates them. The Go wrapper copies frame buffers again. Displaying only one image therefore does not imply one-frame allocation or execution time. A 40MP per-image guard does not bound the number of frames.
2. **WASM failure containment:** `decode_wazero.go` creates a default runtime and passes background contexts to allocations, compilation, and decoder calls; initialization and module instantiation include `panic(err)`. WASM traps can return errors, but the existing wrapper does not prove protection against host OOM, initialization panic, or prolonged execution. This is a source-derived risk, not an observed application crash.
3. **WASM config coverage:** `DecodeConfig` limits its input to 262,144 bytes. Files whose required metadata is beyond that prefix need testing; being rejected would be an availability limitation, not evidence that all HEIF inputs are malformed. Registered major brands are `heic`, `heix`, `hevc`, `hevx`, `msf1`, omitting generic `mif1`. Simply registering `mif1` is also unsafe without codec discrimination because AVIF may use that generic brand.
4. **Pure Go color:** the package states that nclx matrix/range are used, but primaries and transfer are reported rather than applied; RGB remains in the file's own space. ICC bytes are exposed, not converted. A Display-P3 or HDR phone image cannot be claimed correct on the current 8-bit display path on this evidence.
5. **Pure Go transforms and limits:** `Options.AutoRotate` defaults false; `DecodeConfig` reports untransformed dimensions. `FrameSizeLimit` can be explicitly set to 40,000,000, and `Threads` can be bounded. Its `Decode` has a one-frame sequence path; `DecodeAll` is separate. These are promising controls, but require a tailored integration and tests rather than global blank registration. Upstream generic-brand forwarding also touches AVIF sniffing, which must be regression-tested.
6. **Native fidelity:** libheif advertises primary-image selection, alpha, crop/mirror/rotate, color profiles, HDR, grids and sequences. The C API supports selecting the primary image and security limits. This does not establish that a particular wrapper uses all of those features correctly or that output is transformed into the app's display space.

## First-image behavior to validate before implementation

For an image collection, use the **declared primary display image**, not the first thumbnail, alpha/depth auxiliary image, or arbitrary item ID. For a timed sequence without a usable primary still, use the **first display frame only**, including that frame's required dependencies. Do not decode all subsequent frames merely to discard them. Unsupported/ambiguous arrangements should fail with an import error rather than silently selecting an auxiliary image.

This is an implementation acceptance proposal, not a new product decision in `docs/DESIGN.md`. No multi-image behavior has been implemented or verified.

## Recommendation and prerequisites for revisiting

Keep HEIC/HEIF unregistered and out of the picker. Users can externally export a supported PNG/JPEG before importing, accepting whatever metadata and color conversion their exporter performs. Existing formats and the 40MP policy remain as implemented. Issue #6 should stay open at this investigation/review gate; no commit, push, PR, merge, or closure has been performed.

A future validation pass needs:

1. A working Windows Go toolchain (1.26.4 or later if evaluating the inspected h265 version), pinned dependency revisions and a reproducible build environment.
2. Consented or clearly licensed photos from actual phones: 8/10-bit, 12/24MP and 48MP over-limit, tiled/grid, all applicable rotations/mirrors/crops, alpha, sRGB/P3/ICC/HDR/gain map, collection/sequence/thumbnail/auxiliary combinations, Unicode paths, and malformed/truncated/mismatched coded dimensions. Public codec fixtures can supplement this matrix but cannot stand in for it.
3. A reproducible subprocess measurement harness: report machine/OS/architecture, exact fixture hash/provenance, cold-start and warmed `DecodeConfig` + decode + BGRA conversion durations, and Windows process peak working set/private usage. Run malformed and large files under an external wall-time and memory budget; record termination/crash outcomes. Go allocation counts alone miss WASM/native memory and are not peak process memory.
4. Boundary tests at 40,000,000 and 40,000,001 pixels, including contradictory headers, oversized coded tiles/alpha, and sequences with many frames. Verify actual output dimensions before creating native bitmaps. Compare orientation, premultiplied alpha, and color against trusted references. Rerun existing format tests, especially AVIF generic branding.
5. An agreed acceptable import-delay and peak-memory budget on representative hardware, plus a clean Windows VM without Store extensions and Windows ARM64 runtime checks for any architecture promised in distribution.
6. License/notice review of exact shipped components; for native libraries, packaging/source/replacement obligations; for all HEVC implementations, confirmation of distribution patent requirements appropriate to the release.

If isolated decoding, custom color management, native WIC plumbing, or substantial decoder adaptation is necessary, escalate to **large** before implementation and ask the user to select a direction. This investigation does not authorize that restructuring. The least intrusive next experiment is a standalone, non-shipping decoder probe, comparing forced-WASM and explicit-options pure Go decoding against the same corpus; it is not evidence yet for choosing either implementation.
